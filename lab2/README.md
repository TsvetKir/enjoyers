## 2. HTTP-сервис и развёртывание в Kubernetes

### 2.1. Реализация и сборка образа

Для стенда был подготовлен HTTP-сервис api на Go. Из предыдущей версии приложения был перенесён обработчик `/health`. Обработчик `/fail` возвращает серверную ошибку, `/slow` добавляет задержку, а `/load` создаёт пакет HTTP-запросов. Сервис публикует метрики Prometheus, записывает структурированные журналы в формате JSON и формирует трассировки OpenTelemetry.

![Рисунок 6 - Результат автоматической проверки сервиса api](screenshots/image-5.png)

Для запуска сервиса в контейнерной среде был собран образ `lab2-api:0.1.0`. Сборка выполнялась по Dockerfile в два этапа: сначала приложение компилировалось в среде Go, затем исполняемый файл переносился в итоговый образ без компилятора и исходного кода. Для запуска приложения был указан пользователь без прав root. После завершения сборки наличие образа было проверено командой docker image ls.

После загрузки командой crictl images было проверено наличие образа с тегом 0.1.0 в среде выполнения контейнеров узла lab2-control-plane.

### 3.3. Панели RED

В Grafana был создан дашборд «API - RED» и добавлена панель частоты HTTP-запросов - компонента Rate подхода RED. Источник данных - накопительный счётчик `http_requests_total`. Его абсолютное значение не отражает текущую нагрузку, поэтому запрос использует функцию rate с окном в одну минуту. Суммирование по обработчикам и кодам ответа даёт общую частоту запросов в секунду. Минутное окно позволяет наблюдать кратковременные изменения нагрузки. Расчёт включает регулярные проверки `/health` со стороны Kubernetes.

![Рисунок 26 - Настройка панели частоты HTTP-запросов в Grafana](screenshots/image-27.png)

*Рисунок 26 - Настройка панели частоты HTTP-запросов в Grafana*

На дашборд была добавлена панель доли серверных ошибок - компонента Errors подхода RED. Показатель рассчитывается как отношение частоты HTTP-ответов с кодами 5xx к общей частоте запросов за последнюю минуту и отображается в процентах. Он характеризует распространённость ошибок с учётом количества обращений к сервису. В расчёт входят и проверки `/health` со стороны Kubernetes. На показанном временном интервале доля серверных ошибок составляла 0%.

![Рисунок 27 - Настройка панели доли серверных ошибок в Grafana](screenshots/image-26.png)

*Рисунок 27 - Настройка панели доли серверных ошибок в Grafana*

Для оценки задержек была добавлена панель 95-го перцентиля времени обработки запросов - компонента Duration подхода RED. Функция histogram_quantile рассчитывает p95 по гистограмме `http_request_duration_seconds_bucket` за последнюю минуту. Данные обработчиков суммируются с сохранением границ бакетов. Перцентиль характеризует верхнюю границу времени обработки примерно 95% запросов и помогает отслеживать медленные ответы. Это приближённая оценка: её точность зависит от границ бакетов. На показанном интервале p95 составлял около 4,75 мс. Верхняя граница первого бакета - 5 мс, поэтому точные длительности быстрых запросов внутри него по этой гистограмме определить нельзя.

## 10. Заключение

В результате выполнения лабораторной работы в локальном кластере Kubernetes был развёрнут стек наблюдаемости HTTP-сервиса api. Приложение и компоненты стека устанавливались и настраивались с помощью Helm.

Сбор метрик был организован средствами Prometheus. В Grafana был создан RED-дашборд, отображавший частоту запросов, долю серверных ошибок и p95 времени обработки. Запросами к маршрутам `/load`, `/fail` и `/slow` была проверена реакция графиков на изменение нагрузки, возникновение ошибок и увеличение задержки.

Для запроса `/slow` была обнаружена длительная вложенная операция `slow-op`, а для `/fail` - признак ошибки и событие exception. По совпадающему `trace_id` была установлена связь между записью журнала в Loki и трассировкой в Jaeger.

Были настроены и проверены три критических оповещения: высокая доля серверных ошибок, превышение допустимого p95 времени обработки и отсутствие доступных целей сбора метрик API. Их срабатывание было проверено в Prometheus, Alertmanager и Karma. Локальный webhook-приёмник получил уведомления о срабатывании и завершении `ApiHighErrorRate`.

После экспериментов приложение было восстановлено, а работоспособность компонентов стенда проверена повторно. Проверки охватили рост нагрузки, ошибки HTTP 500, задержку ответов и остановку приложения.
